## Existing dependency sequence (source facts)

1. `Auth.init/verifyToken` (`auth.js:55–110`) verifies via bounded `/api/auth/verify`. `startViewer` (`webrtc.js:2694`) awaits `Auth.whenReady` before beginning the startup episode and before marking `start-click` and `bootstrap-start` (`2718–2719`). The real user click can therefore precede the reported start mark. No extra verification request is made by `whenReady` itself.
2. `startViewer` awaits `requestExplicitViewerAdmission` (`2722`, definition `2874`). Ordinary human startup POSTs `/api/auth/viewer-admission` with a 5000 ms bound and current-auth/episode guards; a proof-bearing page skips this ordinary admission. This is an authority dependency for the socket, not a redundant auth request. The fixed evidence does not establish its individual duration or branch from these marks.
3. Only after admission, `createSignalingSocket(true)` runs, immediately followed by `controller.load` (`2738–2744`). The socket can connect while bootstrap is pending; `_deferPeerUntilConfig` is intended to hold media configuration until the snapshot is applied. `init` applies the snapshot, sets the attempt/deadline, reuses the socket and creates the PC (`2566–2600`). It does not fetch configuration again when a snapshot is supplied.
4. Verified auth also preloads `ViewerBootstrap.load` (`7600–7621`). `bootstrap-controller.js:load` coalesces matching inflight mode/TURN/scope and reuses a nondegraded completed snapshot younger than 3000 ms. A refresh after expiration, changed scope/mode/TURN, forced load, or degraded result is intentional; two call sites do not prove duplicate HTTP requests. The 910 ms mark span includes admission, lookup/reuse and any remaining bootstrap work, not necessarily a full request.
5. Socket creation is `io(socketBase, buildSignalingSocketOptions(...))` (`2819–2853`); current transport policy is WebSocket first with bounded polling fallback (`2997–3030`). `signal-connected` marks Socket.IO namespace `connect` (`3786`), not Manager creation, Engine open, HTTP upgrade completion or application welcome. None of those intermediate boundaries is available in the fixed marks.
6. Server application `connected` includes hostOnline/capabilities (`signaling.js:1127`); Viewer then requests `control-acquire` (`webrtc.js:3826–3840`, `4054`). Host online is registration presence, not permission to skip reset. Server initiates a control transition; Host `on_control_transition` awaits initialization and serializes/reset-applies it (`host.py:3303`). Signal consumes `control-transition-ack` and sends `control-grant` only after confirmation (`signaling.js:1259–1298`). This is the actual Host readiness barrier; no distinct `host-ready` event was found on this path.
7. `handleControlGrant` calls `createOffer` (`webrtc.js:4219–4231`). Offer creation requires active control; it does createOffer→setLocalDescription and, in relay mode, an explicit gathering wait before emission (`5577–5650`). That mode-specific wait is existing policy, not evidence of the R5 cause. Signal validates authority and forwards (`signaling.js:1324`).
8. Host `on_offer` takes `_offer_lock`, validates signal/lease/attempt authority, closes the old peer, creates the track/PC, sets remote description, creates answer, sets local description, then waits for `ice_complete` (5 s bound) before emitting the answer (`host.py:3641–3965`). Gathering-complete event sets the event (`3802`), so the explicit wait is not automatically an extra five seconds. No measured duration splits these operations; no installed aiortc internals were executed or assumed.
9. Viewer answer listener awaits setRemoteDescription (`3884–3908`); ICE/PC transitions, track attachment, play and decode/presentation follow. `ontrack` attaches stream and calls `play` (`4727–4752`). `onPeerConnected` starts stats and rVFC tracking (`4479–4528`); element callbacks and stats also feed readiness (`4775`, `notePaintStats`, `markMediaAttemptReady:1175`). The historical `first-frame` mark therefore does not identify which readiness observer fired and does not prove nonblack pixels, fresh source capture, native input, or optical presentation.

## Actionable findings and hypotheses

**Established observability defect:** reported start duration omits `Auth.whenReady` time and conflates explicit admission with bootstrap. Preserve the current compatibility marks, add actual handler-entry/auth/admission/bootstrap request/cache boundaries, and label the existing interval accurately. This is a measurement correction, not proof startup itself is delayed by authentication or admission.

**No established avoidable duplicate request:** verify, explicit admission, and bootstrap serve different contracts. Warmup/load has bounded coalescing/cache. No fixed request counts are available to show cache misses/aborts/retries wasting this attempt.

**Potential safe overlap to evaluate, not an authorized implementation or measured saving:** on a cold/expired bootstrap, begin an inert authenticated configuration fetch while admission is pending, keeping all socket/control/media work behind successful admission and preserving cancellation/scope checks. Verified preload already provides this overlap when usable. Measure admission duration, bootstrap cache disposition and actual fetch timing first; maximum saving cannot be asserted from 910 ms.

**Diagnostics await is a conditional scheduling concern:** socket `connect` listener awaits `Diagnostic.replayPendingDiagnostics` before its own PC/rebind/replay work (`3791–3808`); replay sends at most two diagnostics sequentially (`diagnostic-core.js:488`). This does not block dispatch of separate `connected`/control events, and `init` also creates a PC. No evidence shows this await was populated or on R5's critical path. Instrument queue count and local duration before considering nonblocking replay; do not call it a confirmed startup blocker.

**Conditional PC race to inspect only if observed:** a fast application welcome/control grant can arrive while bootstrap is pending; `handleControlGrant` can create a PC/call offer, while `init` later creates a PC again. `_deferPeerUntilConfig` protects some socket handlers but is not checked by the grant handler. Source permits a competing ordering; fixed marks (bootstrap-ready precedes signal-connected) do not establish that race in R5. A distinct PC-created counter and config-applied mark can confirm/exclude it on future authorized startup. Do not change authority or configuration based on this hypothesis.

**No link/QoS attribution:** steady-state candidate RTT (~36 ms mean) does not decompose HTTP/socket admission/ICE or firstframe, and later pacing excess is not evidence it caused startup delay. Existing QoS/pacing root cause remains unresolved.
