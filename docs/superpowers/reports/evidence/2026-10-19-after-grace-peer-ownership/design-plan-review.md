## Important: make real MediaActivity runtime mandatory in the recovery fixture

Location: plan Task 1 Step 2, lines 53 and 81, and its first regression's final input assertion (lines 110–114); design behavior contract 6.

The prescribed setup explicitly loads `loadWebRTC({realInput:true})` and real `webrtc-stats.js`, but neither that helper nor the specified additional load initializes the MediaActivity controller/runtime. `loadWebRTC` loads real Input and other dependencies but not `media-activity-controller.js` or `media-activity-runtime.js` (`webrtc.test.js:94–207`). In their absence, `initializeMediaActivity` returns a synthetic active snapshot (`webrtc.js:597–603`), `getMediaAppliedPhase` defaults to active (`:678–680`), and `canEnableDesktopInput` treats an absent runtime as allowed (`:686–690`). Thus a conscientious implementation following the explicit recipe can produce a valid stale-peer RED and a subsequent GREEN while never exercising the applied-media ACK/fresh-resume proof required by the spec. “若媒体 runtime 需要 ACK” makes this safety coverage optional even though this fixture silently bypasses it by default. The separate lifecycle test command does not exercise that missing contract in the new recovery chain.

Minimal revision, within existing file scope:

1. Require loading the real `media-activity-controller.js` and `media-activity-runtime.js` into the VM before scenario setup. Let the real `initializeMediaActivity` / grant/replay path create and use them; assert both controller and runtime exist, and that the emitted request/baseline identifies the current attempt. Do not copy the simplified runtime object or `runtime=null` technique from the retained-peer reference fixture.
2. Replace the optional ACK sentence with an explicit requirement to deliver matching simulated Host acknowledgements through real `handleMediaActivityAck`, using the actual emitted request's generation/attempt. Keep real Input reset acknowledgements separate.
3. In the changed-grant regression, show input remains closed without a current matching media ACK/resume proof even when other prerequisites are satisfied, then show matching ACK plus a current post-baseline rVFC (and required mouse/keyboard ACKs) opens it. Late prior-attempt media ACK/frame must not supply the new proof. No direct `markMediaAttemptReady`, runtime phase assignment, or always-true gate stub.

This is a test-plan correction, not a request for more product code, diagnostics, a new framework, or runtime qualification work. The proposed minimal source condition remains suitable.

## Approved design/preflight aspects

- `this.pc && mediaLeaseChanged && !peerLease` extends precisely the missed case. With no previous media association, first grant still does not retire an unleased peer; matching healthy lease still uses existing same-peer logic; an explicitly different peer lease retains its pre-existing retirement path. The intended condition does not add a second attempt increment or change control validation.
- Current retirement ordering is compatible with the extension: `cancelDataChannelWatchdog()` first retires the old channel owner and cancels watchdog/recovery; peer event properties are cleared; current peer/channel references and offer epoch are invalidated; ready/paint is cleared and keepalive stopped before `close`. Actual grant/changed attempt precedes reconcile/new peer creation. Consequently synchronous close callbacks cannot recover the old ownership, and the new callbacks capture the final attempt.
- Peer, video hook, fallback, stats and rVFC callbacks use immutable peer/attempt/sequence identity checks. `retired=true` is an existing invalidation flag, not an identity transfer. A pre-grant connected peer's old stats sampler is replaced/stopped by current `startStats`; old rVFC is canceled/replaced by current `startVideoFrameTracking`. The tests should prove these existing mechanisms, not demand an unrelated lifecycle rewrite.

The prescribed first failed peer-identity assertion distinguishes the defect from missing platform methods. Browser PC/DOM/clock/socket mocks are appropriate boundaries, and the existing VM exposes the real methods needed.
