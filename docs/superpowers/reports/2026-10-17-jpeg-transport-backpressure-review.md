## Follow-up: minimal queue.join candidate (no implementation)

A per-JPEG producer gate on the captured current Engine.IO queue's `join()` is a smaller candidate than changing the global queue or serializing all Socket.IO traffic. In the normal successful writer path, it covers both pending queue and dequeued writer batch: asyncio.Queue.get/get_nowait do not decrement unfinished tasks; Engine.IO calls task_done only after each WebSocket send await returns (async_client.py682–685). The polling path calls task_done after the HTTP await and before checking HTTP success (663–676). Thus join is local writer completion/discard accounting, NEVER remote receipt or delivery proof, and does not bound bytes already accepted by aiohttp/OS buffers.

For one serial relay producer, awaiting this gate before every new capture/admission, including the first frame of a replacement producer generation on the same connection, would prevent JPEG accumulation in this Python queue/batch from recurring TTL retirement. A canceled old producer does not retract its JPEG, but the successor's gate would still account for that old queue's unfinished binary packet. This is conditional on all JPEG admission paths using the gate and preserving existing single-producer and post-await generation/authority checks. Waiting at only the end of an old producer is insufficient because cancellation would bypass it. A capture interval is another scheduling gap: revalidate captured client/queue and generation before emit. Non-media concurrent producers are outside this narrowly stated JPEG property; queue.join can wait on their traffic too and affect media liveness.

Critical limitations require explicit failure semantics before adopting:
1. WebSocket send failure at engineio async_client.py686–690 breaks the writer without task_done for the failed packet and remainder of the local batch. Cancellation also has no batch task_done finally. A join may therefore hang indefinitely even after transport failure. Timeout must keep JPEG admission blocked, not blindly emit another JPEG and recreate accumulation.
2. Engine.IO `_reset`218–225 drains queued entries with task_done but cannot account for entries already in writer-local batch. base_client._reset130–132 resets state/sid only; it does NOT replace queue. Reusing the same library client may retain orphan unfinished count. A discarded queued packet becoming task_done is not successful send.
3. This application's `_build_socket_client` host.py2167–2168 uses reconnection=False; connect2206 and ensure_connected5490+ replace self.sio after teardown. New client has a new queue. A waiter must capture connection/client+queue identity, and re-check current identity and production authority after its await; completing the old queue never authorizes sending under new connection. Generation cancellation should cancel the waiter, not clear shared queue or fabricate task_done.
4. Queue.join uses an Event: a later put can arrive after unfinished count briefly reaches zero and wakes a waiter. It is not an exclusive reservation, atomic drain-and-admit primitive, or promise all global traffic stays empty. For the strictly single JPEG producer this does not introduce a second JPEG producer; cross-producer concurrency would need separate proof.
5. A ws.send return can hand bytes to lower buffers before network delivery. The gate can close the Python EIO retained-JPEG gap but is not an end-to-end byte ceiling or evidence that this incident is transport-caused.

Binary atomicity: installed socketio `_send_packet`384–391 sequentially awaits eio.send for envelope and attachment, but each installed Engine.IO send descends directly into the UNBOUNDED asyncio.Queue.put. Python3.11 asyncio/queues.py110–135 only awaits if full; default maxsize0 never becomes full, then put_nowait returns immediately. With this installed default path and ordinary synchronous logging, these nested awaits do not yield to another event-loop task between envelope and attachment. That is current implementation behavior, not a Socket.IO public concurrency guarantee: socketio async_client.py223–228 explicitly warns concurrent multi-packet emits need serialization. Replacing queue with a bounded queue or introducing per-packet awaited hooks would add genuine suspension, allowing interleaving/cancellation after envelope but before binary attachment. A gate before the entire existing emit avoids introducing that specific per-packet suspension. No global queue replacement or global emit lock is justified solely by this finding.

Smallest existing observation surface: public asyncio queue.qsize/maxsize reports waiting packet count; public queue.join observes all unfinished accounting including writer batch, but has failure ambiguities above and itself is a behavioral wait, so not added live. Engine.IO write_loop_task.done() and state identify writer liveness (library attributes, not application telemetry). There is no existing public byte counter or local writer-batch length. Private queue._unfinished_tasks minus qsize is only an outstanding dequeued-accounting count; failed batches can orphan it, so it cannot reliably mean currently sending bytes. Existing code has no duration for an individual ws.send await. A bounded observational hook around writer-send would be needed for that exact phase; do not claim queue.qsize alone resolves it. The smallest first diagnosis remains splitting existing JPEG worker processor/delivery phases, with queue count/writer state only supplementary and clearly incomplete.
