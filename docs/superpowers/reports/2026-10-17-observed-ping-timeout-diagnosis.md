## Installed heartbeat logic: what it can and cannot distinguish

Current Signal creates Socket.IO without heartbeat overrides (server.js around196). Installed Engine.IO defaults are pingInterval25000ms, pingTimeout20000ms. Server engine.io/build/socket.js:138–158 creates a ping interval timer; when it fires, sendPacket(ping) then resetPingTimeout(20000ms). On incoming pong, lines103–111 clear that timeout and refresh the ping interval timer. Ordinary message packets do not refresh that interval. The client engine.io-client/build/esm/socket.js:239–250 receives ping, creates pong then resets its45000ms deadline; lines291–300 implement the sum-of-interval-and-timeout close. Observed45003ms is a close match to the client timer mechanism and normal browser scheduling.

Server sendPacket emits packetCreate then queues and flushes; flush only calls transport.send when transport.writable and buffer nonempty. WebSocket transport writable returns true after its send callback. Therefore missing next ping at the client can arise from timer not firing, ping created but held by a non-writable transport, ping handed to transport but not delivered downstream, or other failures of that connection. This run captured no server packetCreate/flush batch/received pong or socket timer state, so it cannot distinguish them. Client pong-created+flush at last ping reduces an application-side unflushed-pong hypothesis; it does not prove server pong receipt. If server never received that pong and its own timeout were healthy, it would normally close about20s after its emitted ping; the later server transport-close event makes that simple scenario less consistent, while leaving timer/transport interactions unproven.

No production code search result touches these Engine.IO ping timers directly; inspected application uses ordinary Socket.IO events.
