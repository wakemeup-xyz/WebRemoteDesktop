## Finding and confidence

The observed stop was concretely Host pre-capture backpressure waiting for JPEG frame ACKs. It was not an intentional media suspension and the evidence does not support a capture worker exception or a continuously blocked Host event loop. The ACKs arrived late (about 6.7–6.9 seconds) immediately after the collector had already failed. The initial cause of that ACK delay remains null: current logs cannot distinguish Viewer→Signal transport delay, Signal scheduling/forwarding, Host receive scheduling, or an image-load/ACK emission delay. Do not claim a particular Cloudflare failure, dropped packet, or irreversible deadlock for this runtime incident.

Separately, the current source has a proven liveness defect: pending frame slots are never expired, even though Signal intentionally uses volatile frame delivery. Dropped frame/ACKs or out-of-order ACKs can therefore stop capture permanently while the socket and control lease remain active. This defect amplifies transient delivery problems and makes the observed stall actionable even though its first delayed hop is not attributable.

## Source mechanisms

1. host.py:897–911: when pending count reaches max_in_flight_frames, _run waits for ACK. A timeout calls note_ack_timeout then immediately continues. The pending map is not pruned, retired, or replaced and no new worker submit occurs. Profile downsizing does not resolve missing slots. With max slots reduced from2 to1, even one old hole blocks production.
2. signaling.js:1787 uses viewerSocket.volatile.emit('relay-frame', data). A frame dropped under a non-writable transport will never produce an image-load ACK, while Host currently retains its slot indefinitely. Volatile delivery can remain appropriate for freshness but needs bounded slot retirement.
3. host.py:868 rejects frame_id <= last_acked_frame_id before removing that frame's own pending entry. ACK99 followed byACK98 leaves98 permanently pending even though both have arrived. Browser handleRelayFrame (webrtc.js:4785–4802) also replaces pending onload and revokes the preceding object URL when a newer frame arrives. A superseded load can therefore leave an older frame unacknowledged without a socket failure. Neither mechanism is proven as the initial trigger of this particular run.
4. host.py:871–875 removes a matched pending entry before rejecting measured RTT>=10000 ms. That late-ACK branch does not signal ack_event, update last_acked watermark, or record a late outcome. With no other pending hole, the next wait timeout allows progress, so this branch alone is a bounded wake delay, not permanent slot retention. Combined with an older hole and prior high watermark, it complicates recovery. The actual late ACKs in this incident were below this10-second cutoff.
5. host.py:975 stats emission is after capture/send. The blocked branch continues before stats, so five-second TUNNEL_RELAY_STATS disappears precisely during ACK stalls. Event-loop summaries preserve pending counts but omit pending age, timeout cumulative totals, worker phase, frame receipt/drop/ACK forwards, and current ACK watermark. Absence of stats is not proof the task died.
6. webrtc.js:4778/4808 subtracts Host wall clock timestamp from Viewer Date.now for ACK payload and latency UI. Host correctly ignores that field for its own RTT calculation, using monotonic send/receive instead. The UI value is cross-clock and should not be called measured network delay. relayFrameAckRttMs exists in latency-monitor metric names but has no production recording caller found; all48 artifact observations honestly show unavailable/count0/null. This is an observability contract gap, not proof RTT0.

## Scoped minimum fix proposal (not implemented)

- Give media-only in-flight entries a bounded, monotonic expiration policy tied to current producer generation. On timeout retire eligible missing entries and permit a fresh latest frame without retaining/replaying old frames. Preserve one running/one pending native worker and bounded memory. Do not change input delivery/replay, control authority, network mode, TURN, tunnel URL, or resolution policy as part of this correction.
- Remove only the acknowledged current-generation pending entry regardless of ACK ordering. Track the high watermark independently using max; reject duplicate/foreign/stale-generation entries by map membership/scope. For matched late ACKs, release slot and wake producer, while recording late/expired outcome separately rather than using stale latency as valid adaptation feedback.
- Ensure ACK/frame scope protects restart/reused-frame-ID cases. Current incoming ACK contains no productionGeneration; simply adding generation checking on Host's own map cannot distinguish a delayed prior producer ACK when frame IDs are reset. Prefer a safe media-only correlation token or non-reused sequence plus current authority binding, retaining legacy compatibility deliberately.
- Record bounded aggregate relay progress on a timer that also runs during backpressure: pending count/oldest age, latest capture/encode/send/ACK age, timeouts/expired/dropped/late counters, worker state, task state, current producer generation. Keep IDs opaque or excluded and retain null for unobserved stage times. Wire measured same-Host-clock relay RTT summaries through a scoped bounded observer if required, otherwise explicitly present it unavailable. Remove cross-clock UI latency interpretation.
- Add focused offline regressions for a volatile frame drop, missing ACK, ACK reordering, superseded image load, >=10s late ACK, suspend/resume generation, stop/start frame identity reuse, and resource bounds. Verify one loss recovers with a fresh frame and no uncertain business input replay. After plan/review and explicit deployment scope, rerun the same real public JPEG lifecycle and full60-second follow-up. Until then publicJPEG remains FAIL and specific first-hop delay remains null; TURN acceptance is separate.

## Additional protocol-scope review requested by parent

Confirmed from actual source, distinct from runtime trigger attribution:

- TunnelRelayStreamer.__init__ (host.py:653–654) resets production_generation and lifecycle generation to0; start() clears/restarts frame_id at0 (host.py:768), while start first calls stop (generation increment) then increments generation again. Recreating a streamer can therefore reuse both frame ID and production generation. No producer-instance nonce is sent. A productionGeneration field alone is insufficient across new instances.
- Host frame payload (host.py:941–956) includes productionGeneration but no connectionAttemptId, control media intent generation, or lease epoch. Signal frame forwarding copies data unchanged (signaling.js:1772–1788). Viewer handleRelayFrame only rejects connectionAttemptId when present, and does not inspect productionGeneration at all (webrtc.js:4703 onwards). It stamps accepted arrivals with the current locally derived mediaResumeScope (webrtc.js:4733), rather than proving the frame was produced for that scope.
- The scope captured by onload correctly fences an old callback which executes after a local scope change. It cannot fence an already queued old frame which arrives after scope change: the latter captures the new local scope. During resumed active/resuming phase, that stale arrival can become fresh-frame proof because its origin generation is not checked. This is a source-level counterexample to complete resume provenance, not proof it happened in this run.
- Viewer startTunnelRelay resets tunnelLastFrameId to0 (webrtc.js:4605) to accept restarted frame sequences. A late prior-stream higher-ID arrival can also advance this high watermark and cause the new lower-ID stream to be ignored. During a normal pause/resume the Host does not reset frame_id, so this start/reset counterexample is distinct from pause/resume.
- Viewer ACK (webrtc.js:4774–4779) carries current lease envelope/frameId/renderedAt/cross-clock latency but omits productionGeneration and frame origin attempt/media generation. Host on_relay_frame_ack checks current viewerId only (host.py:5110–5115) then resolves by frame ID. A delayed ACK from an earlier producer of the same Viewer can match a reused current frame ID.

Minimum M6 protocol design should bind each frame and its ACK to the real authority tuple (attempt, lease epoch, media intent generation, and a producer identity that cannot collide when a streamer is recreated). Viewer should validate the origin tuple before changing frame watermark or constructing current-scope resume proof, then echo it unchanged; Host should validate the same tuple before releasing in-flight slots. Legacy events must have an explicit bounded compatibility path or fail closed according to the existing admission contract, not silently count as current strict lifecycle proof. Offline tests should cover queued old arrival after resume and reused frame ID/production generation after streamer replacement, in addition to old callback completion.
