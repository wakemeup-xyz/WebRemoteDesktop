# TURN 画质、延迟与周期抖动评估

日期：2026-09-05（Asia/Shanghai）
审查基线：`7645862`，当前工作树。此次只新增评估与离线证据；未修改产品代码、配置，未启动/重启服务或操作 Cloudflare tunnel。

## 结论

可以进一步改善画质和耗时。当前存在两个应分别处理的问题：

1. **每约一秒画质跳变：已用当前编码器在无网络、静止画面下复现。** 强制全帧 IDR + 100ms VBV + 受限码率，使关键帧明显变糊，再由后续 P 帧逐步修复。
2. **画面停顿后追帧：发现确定的 RTP 时间基错误。** 当前采集输出 `time_base=90000` 而不是 `1/90000`，实际编码器将正常帧间隔转换为巨大跳跃。其对当前浏览器卡顿的具体贡献仍需修正后同路径 A/B，不能把所有丢帧都归因于它。

此外，1080p 软件编码开销、固定码率上下限及观测缺口压缩了优化空间。既有文档把周期性追帧归因于 Chrome/TURN 的描述，不足以排除这里已复现的 Host 实现错误，应在整改后重新检验。

## 发现（按处理优先级）

### F1 / P1：采集时间基错误，RTP 时间线不连续

位置：`python-host/host.py:1108-1110`、`:1213-1215`；`python-host/h264_videotoolbox_encoder.py:588-594`。

`pts` 已经按秒数乘 90000，返回的时间基却仍是整数 90000。PyAV 时间为 `pts × time_base`；H.264 RTP 使用 90kHz 时钟。[PyAV 官方时间定义](https://pyav.org/docs/stable/api/time.html)、[RFC 6184 §5.1](https://www.rfc-editor.org/rfc/rfc6184.html#section-5.1)。

用 AST 直接执行仓库里的 `next_timestamp`，再调用实际安装的 PyAV 16.1.0 / aiortc 1.14.0 与项目编码器，50ms 间隔的结果：

| 输入时间基 | 连续四帧的 RTP 时间戳（去掉随机起点，32 位） |
|---|---|
| 当前 `90000` | 0 → 2907526144 → 1520084992 → 132643840 |
| 正确 `1/90000` | 0 → 4500 → 9000 → 13500 |

这不是普通 32 位长期自然回绕，而是每帧时长换算出错。aiortc sender 将编码器返回值加随机起点后写入 RTP 头；本机安装代码中未发现后续校正。错误不局限于 TURN，直连也共用该采集方法。

建议优先修正时间基，并使用单调时钟建立会话时间原点，覆盖可变 FPS、暂停恢复和时间前进的测试。必须保留 RTP 时钟正确性与在线恢复验证，不能只检查输出帧非空。

### F2 / P1：短 GOP 与紧 VBV 造成周期性画质劣化

位置：`python-host/h264_videotoolbox_encoder.py:65-80`、`:384-404`、`:524-581`；`python-host/host.py:2541-2542`。

TURN 当前为 `libx264 / ultrafast / Baseline / yuv420p / 单线程 / GOP20 / 100ms VBV`。编码计数每 20 帧强制一次 I 帧，产生 IDR；场景切换检测关闭。运行日志中 720p 的周期中位数为 1.02 秒，1080p 因实际帧率下降拉长到 1.50 秒。

离线方法：使用相同静止文字图连续输入 65 帧，用项目 `_encode_frame` 真实编码，再用 FFmpeg H.264 解码，逐帧对原图计算 RGB PSNR。没有抓取用户桌面，没有连接网络，也没有改运行中 Host。

| 编码条件 | 第39帧 PSNR | 第40帧（IDR）PSNR | IDR 大小 |
|---|---:|---:|---:|
| 当前 1152×720 / 1.8Mbps | 31.93dB | 17.54dB | 18.1KB |
| 当前 1728×1080 / 2.5Mbps | 32.64dB | 19.30dB | 28.9KB |
| 1728×1080，仅纠正时间基 | 32.64dB | 19.30dB | 28.9KB |

同一静止画面在 IDR 处明显改变，随后逐帧恢复；20/40/60帧重复出现。这已经证明编码侧能独立制造用户描述的周期性画质抖动。PSNR 是合成场景的客观指标，不是用户真实桌面的清晰度评分；尚未对用户屏幕做同步逐帧录制。

建议在 F1 处理后评估更长、按实际时间定义的 GOP 与按需 IDR，合并周期 IDR、PLI 和应用关键帧请求的预算，并保留受损帧恢复上限。不能简单全关关键帧。若做渐进帧内刷新，需要先验证浏览器解码与丢包恢复兼容性。

**实施陷阱：不能直接把 `gop=20` 改为 40。** `codec_name_for_gop()` 在 GOP>20 时自动选 VideoToolbox，同时其他码率策略也按 GOP 分支。应先将链路类型、编码器选择和关键帧周期解耦，再比较 GOP；否则实验同时换了编码器和码率策略，结论无效。

### F3 / P1：TURN 1080p 实际被固定在 2.5Mbps，弱网与清晰度两端均失去调节空间

位置：`python-host/h264_videotoolbox_encoder.py:51-62`、`:529-543`、`:609-624`。

relay 的最大目标码率被夹到 2.5Mbps；1080 高度又有 2.5Mbps 最小值。真实 setter 实验请求 0.5 / 2.5 / 4 / 8Mbps，四次最终属性值全为 2.5Mbps。

因此带宽充裕时不能进一步提高清晰度，拥塞反馈要求降低码率时也会被地板挡住。固定分辨率是已有产品约束，但不应让有效目标码率与网络反馈完全脱节。

15:46:17 的日志确认 Viewer 主动请求 1920×1080，Host 按 16:10 屏幕比例编码成 1728×1080；本次不是默认720p上限失效，也不是每秒改分辨率。相对1152×720，像素增加2.25倍，配置码率只增加1.39倍；在相同目标20FPS下每像素预算约下降38%。

建议将分辨率意愿、码率允许范围、真实可用带宽分开管理；高质量配置必须报告实际生效值和限制原因。先验证时间线与发送平滑度，再对高码率做带宽受限测试，不能直接全面抬上限。

### F4 / P2：采集/编码预算紧，缺少分阶段真实延迟观测

位置：`python-host/host.py:1112-1245`、`:1299-1301`；`python-host/h264_videotoolbox_encoder.py:72-77`、`:417`；本机 aiortc 1.14.0 `RTCRtpSender._run_rtp`。

当前路径是 MSS后台抓屏 → BGRA缩放 → VideoFrame拷贝 → x264颜色转换/单线程编码 → RTP分片循环发送。`CAPTURE_STATS fps` 实际是消费者 `recv()` 产出率，不是后台抓屏线程的原始FPS；`capture_wait=0` 也不能证明抓屏本身零耗时。

在线1080p窗口 `recv_total` 中位数26.5ms，加上本次合成文字编码单次测得约24ms中位数，已经接近20FPS的50ms预算。二者来自不同测量，不能相加当成在线精确耗时。编码实验期间机器负载变化明显，同尺寸另一次约38ms，所以不能宣称精确提速比例。只读进程采样时 Host CPU 约97%。

已安装 sender 在一帧的 payloads 上循环发送，没有应用级目标码率 pacer。VBV约束编码输出预算，不等于已经把UDP发送平滑展开。应测编码输出大小、分片数、发送时序和队列，再决定是否增加有界pacing。

目前 `encoderMs / rtpSendMs / endToEndVideoMs` 均为 null，不能把状态栏 RTT 当成鼠标到画面的端到端耗时。优先补精确边界与同钟测量，然后评估降低拷贝、颜色转换、重复静止帧工作，以及受控硬件编码。VideoToolbox历史上的延迟出帧和IDR大小问题仍需验证，不建议直接切回。

现有CSS已对RTT/链路状态栏设置固定宽度与等宽数字（`web-client/css/viewer.css:307-338`）。当前已足以证明视频内容本身存在波动，但没有直接证明用户所说的“画面抖动”是否还包含整个页面的几何位移；后者需单独观察video元素边界，不能宣称完全排除。

## 已做的优化反证实验

仅在独立离线进程调整一个参数，不影响服务：

| 改动（1080p） | 第40帧IDR PSNR | IDR大小 | 判断 |
|---|---:|---:|---|
| 基线 | 19.30dB | 28.9KB | 周期性变糊 |
| VBV从100ms扩大到200ms | 21.76dB | 52.3KB | 仍明显跳变；突发大小约1.81倍 |
| ultrafast改superfast | 19.43dB | 29.1KB | 未消除跳变，编码成本增加风险 |

说明：扩大缓冲并不直接等于增加固定播放延迟；风险来自更大突发与链路排队。不能将这两项孤立改动作为正式修复。

## 后续优化与验证方向

这是一份评估报告，尚未进入仓库约定的正式规划流程。

- 先验证时间基修正后的同一TURN节点、同一分辨率播放连续性；不改变分辨率、GOP、码率等其他变量。
- 再解耦GOP与编码器/路径策略，比较关键帧频率、IDR画质、时间域稳定性与丢包恢复代价；目标是静止文字不再周期性由清晰变模糊。
- 增加有效码率和帧预算观测，评估按带宽上调清晰度/拥塞时降帧率；保留用户的分辨率锁定意愿。
- 在发送时序证据基础上评估pacing、采集转换优化与硬件编码；TURN节点优选需要用户实际访问网络的双端测量，本机RTT不能代表公司网/手机网。
- 同路径至少覆盖静止文字、滚动、拖动、暂停恢复和人为有限丢包。记录逐帧paint间隔、freeze时长、IDR大小、解码/丢帧增量、码率及RTT分位数；需更长持续运行才能评价稳定性。

预期收益：时间基修正有望减少异常追帧与缓冲；关键帧策略优化直接改善周期性画质波动；低拷贝与合适编码后端可以释放帧预算。具体可以降低多少毫秒、能否稳定达到1080p20FPS，当前证据不足以承诺。
