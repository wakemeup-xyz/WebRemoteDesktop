## Main finding

Most required same-Host stage boundaries already exist. Reusing their bounded timing/summary machinery is smaller than a new broad observer. MSS grab, latest-frame age, imgproc executor queue/build/convert, custom H264 encode/packetize, Host loop lag, RSS/resource freshness and input queue/apply timings already use local monotonic clocks. Detailed media joins are opt-in and default OFF. Actual gaps are encoder executor admission/resumption, post-encode sender/packet/send-await duration, completion-independent in-progress stage visibility, and reliable event-window association. Existing wall-clock pacing/log cadence is a separate correctness risk; no wall-clock jump is proven in the incident.

Thus current perf_counter_ns and monotonic_ns measurements are same-Host monotonic in this runtime, but keep stage endpoints in a single declared clock/API and never assume portability without checking. process_time is CPU consumed across this process, not elapsed wall time, thread-specific CPU, or pipeline latency. Do not derive one-way latency from Host/Viewer wall anchors. The prior long-run browser anchor/performance association drift is not proof that CLOCK_REALTIME stepped on the Host; clocks on separate domains need independent evidence. ## Clock effects on pacing, input latency and recovery

Host recv rate control STILL uses time.time at1520/1530 (_last_frame_time), while raw capture-loop pacing and RTP PTS use monotonic clocks. If CLOCK_REALTIME steps backward byD seconds between recv calls, computed elapsed can be negative and asyncio.sleep(frame_interval-elapsed) can request aboutD extra seconds. Forward steps can skip a pace interval. This is a concrete code-level wall-clock dependency, not proof that the5149.8ms incident was caused by a clock adjustment. No bounded paired wall/monotonic delta was recorded to establish such a step. Smallest eventual correction/test is monotonic output pacing with injected rollback/forward clocks; retain wall time only for log association.

CAPTURE_STATS FPS/five-second emission and WRD_FRAME_TRACE_SUMMARY cadence use time.time/self.last_time (1293,1623,1661–1691), so wall jumps can distort window duration/FPS or delay aggregate flush even when inner stage measurements are monotonic. TunnelRelay's loop start/elapsed/rate sleep and its stats window also use wall time (1061,1127–1161), whereas relay in-flight/ACK expiry/feedback uses monotonic milliseconds (980,1034–1077). Its monotonic RelayJpegProcessor encodeMs includes capture/convert/JPEG work and is not this TURN/WebRTC encoder route. Overlay key fade uses wall time but is not control authority. Do not conflate Tunnel JPEG with TURN H264 timing.

Input adapter timing is already monotonic: InputTiming defaults perf_counter_ns, queue/apply boundaries inside adapter; handle_input uses perf_counter for total/lock/executor-await. host.py:2525–2546 local_execute_ms encloses adapter await, explicitly NOT pure native execution. InputAdmissionQueue submits perf_counter_ns; adapter InputTiming begins later, so hostQueueMs excludes the earlier M3 admission wait and must not inherit it. InputFrameCausality uses monotonic_ns/10s expiry and matches capture after applied boundary; Host keyframe cooldown uses monotonic at4072. Fresh-capture recovery uses monotonic condition timeout; asyncio.wait_for/sleep durations are event-loop timer based, not repeated time.time differences. Host protocol receiveTime/executeTime are perf_counter values, not UTC timestamps; never subtract them from browser Date.now.

Host clock_sync response3591–3592 still uses adjacent time.time h0/h1. Viewer latency-monitor.js uses performance.now for pending ACK RTT, metric windows and freshness. Clock-sync rtt subtracts only Host's small h1-h0 duration; arbitrary wall offset is not pipeline duration and the stored offset is diagnostic display only in current file. A wall step during the two Host reads can invalidate/distort that diagnostic. Current monitor does not recover main input latency by subtracting raw receiveTime/executeTime from browser time; preserve this boundary.

Recovery is not globally monotonic yet: Viewer input.js uses Date.now for reliable write/reset/mobile-surface deadlines and late ACK hints (e.g.630,897,1289,1380,1435–1488); webrtc.js uses Date.now for signaling recovery elapsed/12s socket recreation, media health/recovery cooldowns and last decoded age (6329–6350,6024,6488). Browser wall rollback/forward can delay/accelerate rearmed deadlines or conditional recovery decisions, although an already-scheduled setTimeout's relative wait is not continuously recomputed from wall time. This is a separate client audit scope; do not silently rewrite recovery/takeover semantics while addressing Host pacing. Existing invalidation/lease/reset ACK fences must remain unchanged.

Existing detailed traces carry identity fields and emit DataChannel batches every100ms, so do not blindly turn it on or persist raw trace bundles just to obtain a few stage maxima.
