# TURN 性能与每秒画质抖动复核

日期：2026-09-06。代码基线：`d93ff2d`（main）。范围：当前代码、已有离线证据、今日 Host/Viewer 日志及采集器定向复现；Terra High 子代理独立复核采集与验收边界。未启动额外 Viewer、重启服务、改变编码配置或操作 tunnel。

## 结论

**没有全部解决。周期画质脉冲未交付修复，当前真实会话还出现了明显的帧率和调度退化。** 先前报告的总体 `NOT COMPLETE` 正确，但其中“最大 paint gap 138/105ms”“paint continuity passed”及无需重跑连续性窗口的表述证据不足，现撤回这些局部结论。已有时钟、策略封装和恢复控制测试通过不能替代性能验收。

## 复核发现

### P1：生产仍使用已知存在画质脉冲的旧编码策略

`python-host/h264_encoder_policy.py:124-144` 保留 `libx264 / ultrafast / Baseline`、20 帧周期 IDR 和 100ms VBV；生产准入仅允许 `relay-legacy-v1`。当前日志也记录同一策略，1152×720、目标 20FPS、有效码率 1.8Mbps。

已有离线报告 `2026-09-05-turn-quality-latency-review.md` 记录静态画面在 IDR 边界显著降质。这一策略未被合格候选替换；`no-offline-winner` 表示候选失败后保留旧策略，并不表示问题解决。

20 帧 IDR 在实际 20FPS 时约每秒一次；实际帧率下降时，其墙钟周期会变长。因此它是已知画质脉冲来源，但不能据此把当前所有严格 1Hz 的画面位移或停顿都归因于 IDR。仍需对齐实际 IDR、逐帧清晰度、呈现间隔和画面几何变化。

### P1：当前会话性能明显不合格，编码路径耗时高，随后出现 Host 调度 lag

从 `back-debug.log` 固定提取 **2026-09-06 15:45:00（含）至 15:46:00（不含），UTC+8** 的 56 条 `VIEWER_STATS` 和 11 个编码窗口：

| 指标 | 实测 |
|---|---|
| 输出 | 1152×720，selected candidate 为 relay |
| Viewer FPS 最小 / 中位 / 最大 | 1 / 9 / 15，低于原 720p 中位 ≥18 门槛 |
| 接收 / 解码帧增量总和 | 479 / 479 |
| 丢包 / 丢帧增量总和 | 0 / 0 |
| freeze 增量总和 | 8 |
| 编码窗口 P95 的范围 | 65.617–992.603ms；这是不同窗口的 P95 范围，不是整分钟 P95 |
| 编码路径最慢单帧 | 992.603ms |

同一会话后续、上述统计窗口之外，15:46:11 和 15:46:13 的 Host event-loop lag 分别为 441.463ms、513.913ms；系统一分钟 load 为 49.337。15:46:33/38 捕获统计实际约 9/8.5FPS。这些是补充样本，未合入表中一分钟统计。编码指标为 `encode()` 含分包等工作的墙钟耗时，也包含调度等待，不能等同于 x264 纯 CPU 耗时，更不能直接作为端到端延迟。

这些数据确认性能故障，支持优先排查 Host 捕获、转换、编码与资源竞争；它们不支持将本次退化直接归因于 TURN 丢包，也不能排除网络抖动的贡献。没有停止其他程序或通过降低机器负载人为制造通过结果。

### P1：验收采集器会漏掉已经结束的卡顿

`scripts/turn_runtime_collector.py:224-226` 的回调只覆盖 `lastPaintAt`；第 253 行输出的是每秒采样瞬间的帧龄 `now - lastPaintAt`。第 120-124 行却据此验收最大帧间隔。帧龄和两次连续呈现之间的间隔不是同一指标。

本次通过 Node VM 直接执行仓库 `SAMPLE_JS`，注入确定性帧回调：0ms 与 1490ms 呈现，1000ms 与 2000ms 采样。结果：

```json
{"actualInterFrameGapMs":1490,"reportedPaintGapMs":[1000,510],"gateRejects":false}
```

因此先前的 138ms / 105ms 只能解释为采样帧龄最大值，不能证明没有大于 1 秒的呈现间隔。Viewer 已在 `web-client/js/webrtc.js:4520-4549` 记录逐帧 interval、maxGap 和几何变化；采集器却复制另一字段 `_lastPaintStats`。修复应消费可靠的连续观测或维护逐帧累计值，并覆盖窗口边界、尚未结束的 stall、attempt 切换与回调重绑，不能简单换字段后直接判通过。

### P2：捕获优化没有上线，场景与输入验收仍缺失

`python-host/host.py:1358-1361` 仍以目标帧率两倍采集，20FPS 对应 40Hz。旧报告 §9 的 PASS 仅表示未越过准入限制，不能读成 CPU 开销已降低。静止文字、滚动、输入效果和有限丢包仍未完成合格验证；少量未认证场景截图无法证明字符清晰度或排除画面位置抖动。

独立审查另发现候选选择器第 36 行在首个仅通过离线门槛的候选处提前返回，可能遮蔽后续已通过全部运行门槛的候选。它不影响当前所有候选均不合格的结果，也不是此次抖动的原因，应在下一轮候选选择前补齐覆盖。

## 后续修复顺序与关闭条件

1. 先修正验收指标：逐帧间隔及未结束 stall、IDR 时间与原因、帧尺寸和 CSS 几何、输入效果关联；为上述 1490ms 反例及跨采样/跨窗口卡顿建立回归用例。
2. 在真实负载下分解捕获、转换、编码/分包和调度耗时，验证降低捕获倍率等候选的收益及画质影响；不能只在静态低负载桌面上测平均 FPS。
3. 继续比较 GOP、VBV、码率及编码方式的候选，联合考核文字清晰度、周期质量谷值、恢复和耗时。保留当前默认，直至有合格证据；不把简单延长 GOP 等同于问题关闭。
4. 在无其他 Viewer 的维护窗口，用修正后的采集器重新运行 720p 10 分钟、1080p 5 分钟，并覆盖静态文字、滚动、输入、暂停恢复、有限丢包和代表性资源竞争。原有 relay 连通性与时长事实可保留，但不能豁免重跑呈现连续性和性能验收。

本次只完成审查与验收文档纠正，没有实施上述代码修复，也没有宣称画质脉冲或当前性能故障已关闭。
