# 媒体节流与统计窗口的单调时钟修复

状态：待实现和独立 review。属于已有稳定性整改的窄补充，用户已授权完成开发与运行验收。

## 证据与问题

最近一次 TURN 连续测试实际运行约 1922.5 秒，发生 5149.8ms 的浏览器帧回调间隔，三小时验收未完成。同期 Host 日志墙钟回退约 4.24 秒；连接身份和信令心跳保持正常，第二次停帧附近未记录多秒事件循环阻塞。不能靠跨钟相减证明整段因果。

源码提供了可独立复现的缺陷：`ScreenCaptureTrack.recv()` 使用 `time.time()` 计算两次输出间隔，20fps 时，真实经过 20ms、墙钟回拨 4.24 秒，会请求 `asyncio.sleep(4.27)`。这会暂停媒体输出而不阻塞事件循环。`TunnelRelayStreamer._run()` 的迭代耗时也使用墙钟，回拨发生在一次迭代期间会同样扩大节流睡眠。后一条并非本次 TURN 测试实际使用的路径。

两种媒体路径的五秒统计窗口也使用墙钟，可能延迟日志并扭曲 FPS。现有 RTP PTS、采集线程节流、ACK TTL、输入排队期限已使用单调时钟，保留它们。

## 方案选择

采用最小修复：仅将媒体节流及其统计窗口的时间源统一为 `time.monotonic()`。不用截断超长睡眠的补丁掩盖负 elapsed，也不改变系统时间同步、网络路径、帧率或编码策略。无新依赖、协议或后台任务。

## 行为契约

1. ScreenCaptureTrack 的 `_last_frame_time`、`last_time` 和所有对应读写采用同一种单调秒时钟；初始/恢复 sentinel 保持可立即输出，既有暂停及关闭复查保持有效。
2. `recv` 在真实 20ms 间隔、50ms 帧周期时只请求约 30ms 节流；墙钟前跳或回拨均不影响该值。真实耗时已超过帧周期时不补偿连发、不新增等待。
3. JPEG 迭代 `started/elapsed` 及 `stats_started_at/now/duration` 使用单调秒时钟。既有 1ms 最小 yield、ACK/TTL、来源隔离、质量策略和限流不变。
4. 五秒 CAPTURE、frame trace summary 与 JPEG 统计以单调经过时间触发，FPS 分母使用相同窗口。更新测试 fixture 的私有字段时钟，避免混钟。
5. 日志日期、JPEG `timestamp`、已有 clock-sync 协议继续使用墙钟；不能把 epoch 字段替换为单调时钟或宣布跨机器单程时延已测得。未使用的统计私有字段仅在本修复必需时处理，不做无关重构。
6. 离线测试禁止实际 MSS、Quartz、浏览器、网络或服务操作。使用既有 bare track、fake JPEG worker 与 fake clock，执行真实 `recv` / `_run`，不可只匹配源码或重写公式充当回归。

## 验收与局限

先记录旧实现对 ±4.24 秒墙钟跳变的失败，再验证修复后两条路径的正常节流、超时后不补偿、暂停/恢复/关闭及统计窗口。独立 review 后只同步审核过的 Host/测试/文档，保留主工作区 HEAD、index 和用户修改。零 Viewer 时通过既有 helper 仅重启 Host，检查正式入口、Host 在线、原 tunnel/watcher 身份、网页 build 不变。

真实公网短测使用既有一次性 proof 和真实 UI Start；不发送业务输入，不改系统时间制造故障。分别记录 TURN/JPEG 首帧、连续性及恢复，随后继续严格长测。修复解决确定的墙钟节流缺陷，不自动证明第一次 2.7s Host loop stall、历史信令首断、资源压力或全部 5.15s 空窗均已消除。输入到真实可见效果仍需独立可控的原生验收环境，不能由 RTT、ACK 或门禁开放替代。
